# 报销归档批次：需求说明

## REQ-001 归档批次模型（Must）

管理员可创建唯一名称的逻辑归档批次，保存中国自然日的父报销提交日期范围、创建人和固定成员。历史报销迁移后均为未归档。

## REQ-002 归档预览与原子创建（Must）

管理员输入名称和起止日期后可预览完整范围的可归档数量、阻塞原因、报销金额和餐补金额。创建时服务端重新验证；任何状态变化、重复归档或未结案记录均使事务整体失败。

## REQ-003 父子一致性（Must）

餐补通过父报销归档，不允许独立归档。父报销进入批次后，其当前版本餐补在报销详情、餐补看板和导出中均显示同一批次。

## REQ-004 报销管理归档状态（Must）

“全部报销”显示归档状态和批次名称，支持全部、未归档、已归档及具体批次筛选；待审批和待发放队列排除已归档记录；划分方式支持归档批次。

## REQ-005 看板筛选与划分（Must）

报销看板和餐补看板均支持按归档状态、具体批次筛选，并支持按归档批次划分；未归档记录形成明确的“未归档”分组。

## REQ-006 批次精确 ZIP（Must）

管理员可按批次固化成员重新生成 ZIP。ZIP 包含报销汇总、费用明细、行程明细、餐补明细和 `报销凭证/`，跨项目记录保留项目字段；已批准餐补作为独立报销汇总行。导出不重新按日期计算成员。

## REQ-007 名称维护与审计（Must）

管理员可修改批次名称，成员和日期范围不可修改。批次创建、改名和重新导出写入审计日志。

## REQ-008 兼容性（Must）

现有审批、发放、详情、附件、月度 ZIP、普通用户列表和既有 API 行为保持兼容；不引入重大新依赖。
