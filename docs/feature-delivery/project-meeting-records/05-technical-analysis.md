# 项目会议记录：技术分析

## 分析方式

2026-09-03 经用户许可，使用四个只读 subagent 分别检查后端数据库、前端交互、Excel 导出和定时备份；主 Agent 复核项目源码、测试、配置和部署文档。subagent 未修改文件。

## 已验证事实

- 项目是 ASP.NET Core 8 Minimal API、EF Core/Npgsql 和 Vue 3/Element Plus，当前未依赖 OpenXML、ClosedXML、EPPlus、NPOI 或第三方调度框架。
- `WeeklyReport` 已提供项目、作者、最后编辑人、时间戳和并发令牌的可复用模式，但其作者私有查询和项目/作者/周唯一键不适用于共享会议记录。
- `Program.cs` 已有认证路由组、管理员路由组、统一异常返回和个人资料完整性守卫。
- 前端已有周报列表、报销动态条目编辑器、桌面/移动响应式布局和文件下载封装。
- 现有 `XlsxWorkbookWriter` 只支持无样式二维数据，不能支持会议模板需要的样式、动态行、合并单元格和打印设置。
- 新版参考 Excel 为 `A1:I13`、A4 纵向、粗黑边框、黑体表头、29 个合并区域；第 9 行是统一事项表头，第 10 至 13 行是事项数据行。
- 当前唯一后台服务通过 `BackgroundService + PeriodicTimer` 运行；Docker 默认是单 API 实例并使用本地持久卷。

## 后端与数据库结论

- 新增主表 `MeetingRecords`、参会人表 `MeetingParticipants`、事项表 `MeetingRecordItems`。
- 主表保存项目、会议日期、地点、创建人、最后编辑人、删除人、时间戳和并发令牌。
- 子表保存顺序；事项不再设置分类字段，使用会议内全局 `SortOrder`。
- 主表使用软删除查询过滤器；普通查询、详情和导出自动排除，备份内部显式 `IgnoreQueryFilters()`。
- 编辑采用完整子项替换，不提供逐次正文版本；一次 `SaveChangesAsync()` 保证主记录和子项原子更新。
- 所有用户使用同一套查询、创建和编辑接口；管理员删除放入现有 `admin` 路由组。
- 审计只记录项目、日期、子项数量和导出数量，不记录正文、参会人姓名或电话。

## 前端结论

- 新增 `/meeting-records` 页面和“会议记录”导航，所有角色共用。
- 列表只显示概览，编辑前重新读取详情，避免用过期列表数据覆盖他人修改。
- 编辑器拆为独立组件，使用基本信息、参会人员、会议内容摘要三个区域。
- 重复项使用稳定 `clientKey` 和上移/下移按钮，不新增拖拽依赖。
- 409 冲突时保留当前输入并显示持续提示；用户明确执行“重新加载”后才覆盖本地内容。
- 管理员删除使用确认框并携带并发令牌；普通用户不显示删除入口。
- 导出使用独立项目选择弹窗，明确不受页面日期筛选和分页影响。

## Excel 结论

- 新建专用 `MeetingRecordWorkbookWriter`，继续使用 `ZipArchive + XmlWriter`，避免增加依赖和污染现有简单 writer。
- 参会人员预留至少 3 行；统一会议事项预留至少 4 行。
- 事项使用单一“需求内容、状态、截止时间、负责人”表头和动态数据行，保留参考模板的字段、列宽比例、字体、边框和分区风格。
- 工作表按 `MeetingDate -> CreatedAt -> Id` 排序，同日使用 `yyyyMMdd-01`、`yyyyMMdd-02` 命名。
- 长文本使用自动换行和显式估算行高；电话按字符串写入；日期统一 `yyyy-MM-dd`。
- 设置 A4 纵向、`fitToWidth=1`、`fitToHeight=0` 和动态打印区域。

## 备份结论

- 新增 `MeetingRecordBackupOptions`、备份存储/生成服务和后台调度服务，不复用允许删除的附件存储接口。
- 每次启动计算不晚于当前时间的最近周日 02:00 北京时间；目标快照不存在则立即补做。
- 停机跨越多周只补做最近一期，因为当前数据库无法重建历史周当时的数据状态。
- 新格式 ZIP 包含 `manifest.json`、`meeting-records.v2.json`、`checksums.sha256`；既有 v1 备份永久保留。
- 使用可重复读事务获取一致快照，在同目录写临时文件、校验后 `File.Move(..., overwrite: false)` 原子提交。
- 成功 ZIP 永不由应用自动删除；失败删除本次临时文件并重试。
- Docker 增加独立 `meeting_record_backups` 卷，生产卷固定命名并加入部署手册。

## 风险与限制

- 共享记录包含电话，所有用户均可查看，这是已确认权限的直接结果；备份目录必须限制服务器访问权限。
- 永久全量备份会持续占用磁盘，应用只能记录大小和失败日志，容量告警由运维负责。
- 应用内调度适用于当前单 API 实例；未来横向扩容前必须增加数据库锁或分布式调度。
- 领域备份不等于 PostgreSQL 整库备份，不能恢复账号、角色及其他业务。
- 多工作表全量导出会随记录数增长增加内存和打开成本；本期保持现有内存响应模式，后续按真实数据量决定是否改为临时文件流。
