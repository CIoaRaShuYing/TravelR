# 差旅报销 Web：技术分析

## 当前事实

- 工作目录只有本次调研文档，没有可复用的应用、数据库、认证服务或部署约束。
- 因此不采用对现有项目的局部改造，也不依赖 Odoo 或 ERPNext 的运行时。
- 本次由主 Agent 完成只读技术分析，未启用 subagent；原因是当前仓库为空，分析不存在可并行的既有代码路径。

## 推荐技术路线

采用一个可独立部署的前后端分离单体：

| 层次 | 选型 | 原因 |
| --- | --- | --- |
| 前端 | Vue 3、TypeScript、Vite、Element Plus | 适合表单、审核列表和后台配置页面，组件生态成熟。 |
| API | ASP.NET Core 8 Web API、EF Core、ASP.NET Core Identity | 提供账号、密码哈希、角色授权、请求验证和可测试的领域服务。 |
| 数据库 | PostgreSQL 16 | 事务、索引、JSON 审计上下文和本地/容器部署均成熟。 |
| 文件 | MinIO（S3 兼容） | 凭证存入私有对象桶，数据库只保存元数据和对象键。 |
| 部署 | Docker Compose、Nginx | 单机或小规模内网部署简单，后续可迁移到 Kubernetes。 |

## 关键设计判断

1. 不直接使用开源 ERP：首期业务只覆盖注册、报销、审核和私有附件。引入完整 HR/ERP 会增加账号、组织、会计、升级和许可证的维护成本。
2. 不拆微服务：注册规则、报销状态流转、附件授权和审计需要一致事务边界，首期单体更易验证和部署。
3. 凭证与费用条目分离：同一费用可附多个文件，且一个 PDF/图片不等同于一笔金额，避免多张票据时无法正确汇总。
4. 住宿可选：`TravelClaim` 在提交时只验证 `DepartureTransport` 与 `ReturnTransport` 各至少一条；`Lodging` 可为零到多条。
5. 注册模式必须由服务端判定：前端只负责展示，注册接口每次都读取当前设置，避免通过直接调用接口绕过“不开放注册”。

## 风险与处理

| 风险 | 处理 |
| --- | --- |
| 发票图片或 PDF 泄露 | 私有对象桶、下载接口做对象级鉴权、短期授权链接或代理下载、全程审计。 |
| 伪造文件或恶意上传 | 限制 MIME/扩展名/大小，读取文件签名；预留病毒扫描适配器，扫描失败不得对审核人开放。 |
| 报销被重复提交或重复审核 | 以乐观并发字段和状态条件更新控制；审批记录只追加，不覆盖历史。 |
| 管理员误切注册模式 | 记录配置变更审计；模式只影响新注册，不回收既有账号。 |
| 未来接入财务系统 | 用稳定的报销单号、状态事件、导出接口隔离；首期不直接写入外部总账。 |

## 不采用的方案

- Odoo/ERPNext 直接使用：无法无改造满足行程必填规则与注册审核策略。
- 在 Odoo/ERPNext 二次开发：仅在组织已经部署其平台且需要会计/薪酬深度集成时才有较高收益。
- 前端直传公开文件存储：不满足报销凭证的私有访问与审计要求。
