# 差旅报销 Web：业务边界

## 业务目标

让合格用户在线提交可追溯的差旅或普通费用报销，并使管理员控制谁可以注册、谁可审核、哪些凭证构成一次完整差旅行程。

## 角色

| 角色 | 负责事项 |
| --- | --- |
| 访客 | 在允许时提交注册申请；不可访问报销数据。 |
| 申请人 | 创建、编辑草稿、提交自己的报销单，查看审核进度。 |
| 审核人 | 审核已提交报销单，批准或驳回并记录意见。 |
| 管理员 | 配置注册模式、审核注册申请、配置费用类型、管理用户与报销权限。 |
| 财务（可选） | 复核、登记付款、导出对账资料。 |

## 核心对象

- 注册设置：`开放注册`、`管理员审核注册`、`不开放注册`。
- 注册申请：待审核、通过、拒绝；通过后才产生可登录账号。
- 报销单：类型为 `差旅行程` 或 `单据报销`，包括说明、申请人、金额汇总、状态、审核轨迹。
- 行程：报销单中的一次完整出行，必须包括出发交通与回程交通凭证；住宿始终为可选类别，不构成提交门槛。当天往返允许出发日期与返程日期相同且不录入住宿。每类均允许有多张票据。
- 费用凭证：类别、金额、日期、商户/说明、图片或 PDF 附件。
- 审核记录：动作、意见、操作者、时间、前后状态。

## 数据与权限边界

- 申请人只能读取和变更自己的草稿或被驳回单据；提交后不得绕过流程篡改。
- 审核人仅能处理授权范围内的报销单。
- 附件必须为私有文件，下载链接需要鉴权，并记录上传、替换、删除和下载审计。
- 当系统不存在任何 `Administrator` 用户时，首位访客注册是系统初始化流程：不受三态注册策略阻断，注册完成后同时获得 `Applicant`、`Reviewer` 和 `Administrator` 角色。
- 首位管理员创建后，管理员切换注册模式只影响后续新注册，不应使已注册用户失效。

## 首期明确不做

- 不做机票/酒店预订、差旅审批预申请、自动比价。
- 不做发票 OCR、税务验真、自动重复报销识别、自动付款或银行直连。
- 不替代总账、薪酬或 ERP；如需对接，采用后续接口集成。

## 关键假设与风险

- “完整行程”按去程和回程交通的类别完整性校验，而非要求每种类型恰好一张票据；住宿不参与完整性校验，也不因行程日期而变为必填项。
- 当天往返是合法行程：出发日期可等于返程日期，且住宿条目可以为零；有住宿时仍支持一晚或多晚、多张票据。
- 用户可保存未完整行程为草稿；提交时必须校验去程交通、回程交通、报销说明和至少一项有效金额。
- 住宿发票可能为多晚或多张；出发/回程交通也可能各有多段，模型需支持多附件和多费用条目。
- 页面只能提示“当前可创建首位管理员”，最终资格仍由服务端串行化事务在提交时判定，避免两个并发访客都被授予管理员角色。
