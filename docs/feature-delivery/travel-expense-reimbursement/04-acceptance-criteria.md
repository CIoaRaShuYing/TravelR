# 差旅报销 Web：验收标准草案

## REQ-001 至 REQ-004：注册治理

- Requirement: 管理员可设置三种注册模式。
- Acceptance criteria: 开放注册时新用户注册后可登录；审核注册时账号在管理员批准前不能登录；已有管理员且不开放注册时，访客通过页面和直接接口均不能创建账号。系统没有管理员时，首位注册不受三态策略阻断，并获得申请人、审核人、管理员三个角色。既有账号不受模式切换影响。
- Verification method: 使用三个不同测试邮箱逐一执行注册与登录；调用注册接口验证服务端拦截；检查管理员创建账号仍可用。
- Test data: 三个未注册邮箱、一个已有有效账号、一个管理员账号。
- Risk: 只隐藏前端注册按钮会造成接口绕过。
- Status: done（隔离 PostgreSQL 真实 HTTP 验证：审核注册为 202 → 401 → 200；关闭注册接口为 400；开放注册为 200 → 200。）

## REQ-015：首位管理员注册引导

- Requirement: 首位注册必须明确建立管理员账户，注册成功后进入登录界面。
- Acceptance criteria: `GET /api/registration-settings` 在系统无管理员时返回首位管理员注册可用状态；注册页展示高优先级提示，明确列出管理员、审核人、申请人权限；即使注册模式为 `Closed` 也显示首位管理员注册按钮。首次注册成功后页面切换到登录表单、手机号自动带入、密码不保留；待审核申请只提示等待审核，不切换为“注册成功”。
- Verification method: 空管理员数据库分别在 `Open`、`ApprovalRequired`、`Closed` 模式读取公开设置并检查页面；提交首位注册后检查响应、角色和登录表单切换；已有管理员时复测三态策略。
- Test data: 一个未注册手机号、一个空管理员数据库、三种注册模式。
- Risk: 页面状态可能在并发时过期，因此页面提示仅用于引导，服务端事务是角色授予的最终裁决。
- Status: done（唯一命名的临时 PostgreSQL 数据库真实 HTTP 验证：`Closed` 模式仍返回 `initialAdministratorRegistration: true`；首位注册返回 `registrationCompleted: true`、`initialAdministrator: true`；登录角色同时包含 `Applicant`、`Reviewer`、`Administrator`。前端生产构建通过，桌面与 390px 移动布局无横向溢出。）

## REQ-005 至 REQ-008：报销录入

- Requirement: 同时支持完整行程报销和独立单据报销。
- Acceptance criteria: 行程草稿可保存；缺少去程交通、回程交通任一类凭证或缺少说明时不可提交并提示缺项；补齐后可提交。住宿条目可为零且不因行程日期变为必填；当天往返可填写相同的出发/返程日期并在不上传住宿凭证时提交；独立单据报销不要求行程票据，但必须有说明。
- Verification method: 分别建立缺去程、缺回程、无住宿的当天往返、含住宿的完整行程、办公用品单据、聚餐单据六组测试数据。
- Test data: JPG/PDF 附件、金额、日期、费用类别和说明。
- Risk: 将“凭证图片”与“费用条目”混为一体会影响多张票据和金额汇总。
- Status: done（隔离 PostgreSQL/MinIO 真实 HTTP 验证：当天往返零住宿两张 PDF 凭证上传后可提交；办公用品与聚餐两项普通单据各上传凭证后可提交。）

## REQ-009 至 REQ-010：审核和审计

- Requirement: 提交、批准、驳回和重提均可追溯。
- Acceptance criteria: 申请人提交后不能自行审批；审核人批准或驳回均形成带时间、人员、意见的记录；驳回单修改后可再次提交，保留历史记录；未授权账号不能读取其他人的私有附件。
- Verification method: 双账号权限测试、状态流转测试、审计记录查询、附件越权访问测试。
- Test data: 申请人、审核人、无权限用户各一个；一张已提交报销单和一份私有附件。
- Risk: 未设置对象级权限会造成报销单或发票附件泄露。
- Status: done（真实 HTTP 验证：提交、批准、驳回、修改并重提的审批记录可回读；未登录附件下载为 401，其他申请人为 403。）
