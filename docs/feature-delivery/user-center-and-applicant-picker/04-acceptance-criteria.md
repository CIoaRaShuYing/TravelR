# 用户中心与申请人筛选修复：验收标准

## REQ-UC-001 / REQ-UC-002：用户中心列表

- Requirement: 管理员可查看正式用户并筛选。
- Acceptance criteria: 管理员登录后能从桌面菜单和移动端抽屉进入“用户中心”；页面显示姓名、手机号、角色、启用状态；按关键字和状态筛选后分页结果与服务端总数一致；响应中不存在 `PasswordHash`、`SecurityStamp` 等认证敏感字段。
- Verification method: 后端构建/测试；接口静态检查；管理员 HTTP 调用；前端生产构建；浏览器桌面与 390px 移动布局检查。
- Test data: 1 个管理员、至少 2 个申请人（其中 1 个开放注册且无报销）、1 个停用用户。
- Risk: 只在前端隐藏入口会造成接口越权。
- Status: passed（管理员真实 HTTP 返回 3 个正式用户，关键字与分页参数生效，响应不含认证敏感字段；桌面浏览器显示用户表格，390×844 移动端显示用户卡片且无横向溢出。）

## REQ-UC-003 / REQ-UC-004：账号启停与权限

- Requirement: 管理员可启停，申请人不可管理。
- Acceptance criteria: 管理员停用用户后，该用户下一次鉴权请求按现有 JWT 校验失败并需重新登录；启用后可重新登录；操作写入 `AuditLog`；普通申请人调用用户列表和启停接口分别得到 403；不发生用户或历史报销物理删除。
- Verification method: 后端接口验证、审计记录查询、现有用户停用后的鉴权验证、自动化测试。
- Test data: 管理员和申请人各 1 个正式账号。
- Risk: 停用当前管理员可能立即失去后续操作权限，应在页面上要求确认并提示影响。
- Status: passed（普通申请人访问用户目录返回 403；停用后旧 JWT 请求返回 401，重新启用后可恢复；当前管理员自停用返回 409；启停与审计写入在同一 `SaveChangesAsync` 中提交。）

## REQ-AP-001 / REQ-AP-002 / REQ-AP-004：申请人目录完整性

- Requirement: 申请人下拉不再依赖已有报销。
- Acceptance criteria: 当 A 用户为开放注册直接创建、B 用户为管理员批准创建，且两人均无报销时，管理员打开报销管理的申请人下拉可同时看到 A、B；待审批申请和无 `Applicant` 角色账号不可见；停用用户不可见。
- Verification method: 隔离 PostgreSQL 或现有测试数据库中构造注册/审批/停用数据，调用申请人目录接口并执行浏览器下拉验证。
- Test data: 开放注册用户、批准注册用户、待审批申请、管理员账号、停用申请人。
- Risk: 将用户目录与报销分组混用会导致无报销用户再次丢失。
- Status: passed（隔离 PostgreSQL 真实 HTTP 验证：开放注册用户和批准注册用户在均无报销时同时出现在申请人目录；停用后目录排除、启用后恢复；浏览器下拉显示无报销的开放注册用户。）

## REQ-AP-003 / REQ-AP-005：筛选与汇总兼容

- Requirement: 目录查询可扩展，分组汇总语义保持不变。
- Acceptance criteria: 输入姓名或手机号关键字后只返回匹配的启用申请人；分页字段有效；选中申请人后报销列表按其 ID 查询；按申请人分组时仍只显示当前筛选条件下有报销的人员和金额，不凭空生成零金额分组。
- Verification method: API 参数验证、前端构建、浏览器筛选/分页/分组交互检查。
- Test data: 至少 3 个申请人、2 个有报销、1 个无报销。
- Risk: 目录接口与报销列表接口分页参数不一致会造成下拉空缺。
- Status: passed（姓名和手机号关键字查询、`pageSize=1` 分页参数通过；选择项仍使用用户 ID；无报销环境的分组账本保持空结果，没有生成零金额分组。）
