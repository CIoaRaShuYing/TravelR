# 用户中心与申请人筛选修复：需求接收

## 用户原始目标

- 当前代码缺少用户中心管理界面。
- 无需管理员审核后注册的用户，在报销管理的“申请人”下拉中找不到。

## 推断出的业务目标

在保留现有 `Applicant` / `Administrator` 两角色模型、注册审批流和报销流程的前提下：

1. 管理员可以在独立的用户中心查看系统用户及其角色、启用状态和基础账号信息，并能管理账号启停。
2. 报销管理的申请人筛选应来自全部可作为申请人的正式用户，而不是仅来自已经存在报销的聚合结果。
3. 开放注册用户、管理员批准后的用户，只要已经成为正式 `Applicant` 账户，即使尚无报销，也必须出现在申请人筛选中。

## 当前已知约束

- 后端为 ASP.NET Core 8 Minimal API + EF Core + ASP.NET Identity + PostgreSQL。
- 前端为 Vue 3 + TypeScript + Vite + Element Plus。
- 业务角色保持 `Applicant` 和 `Administrator`，不新增独立审核人角色。
- 账号停用必须通过现有 `AppUser.IsActive` 影响登录和 JWT 有效性；不物理删除用户。
- 不修改注册审批合同，不绕过后端授权，不把申请人筛选改成前端本地拼接。
- 不记录密码、密码哈希或其他敏感认证数据到用户中心响应或日志。

## 暂定假设

- “用户中心管理界面”指管理员可访问的用户列表与账号启停界面，而不是新增用户自助改密流程。
- 用户中心默认展示正式账户，不展示 `RegistrationRequest` 待审批记录；待审批记录继续由“注册审批”管理。
- 当前 `AppUser` 没有持久化创建时间字段，本轮用户中心不新增 Identity 表字段，列表不展示创建时间。
- 申请人下拉展示全部启用的 `Applicant` 角色用户；管理员如果同时拥有 `Applicant` 角色，也可作为申请人被筛选。
- 申请人列表支持服务端关键字筛选和分页，前端下拉只加载当前需要的候选集；本轮不引入项目成员关系。

## 本轮范围

- 新增管理员用户列表 API、用户账号启用/停用 API。
- 新增管理员用户中心页面、路由和桌面/移动端导航入口。
- 新增申请人目录 API，并让报销管理申请人下拉改用该目录。
- 增加后端/前端静态验证与必要的单元测试。

## 本轮不做

- 不新增用户、重置密码、修改手机号或修改角色的管理操作。
- 不删除用户及其历史报销、附件、审计记录。
- 不改变注册策略、注册审批状态机、报销审批或发放状态机。
- 不维护项目成员名单。

## 待确认事项

- 是否接受上述“用户中心仅管理正式用户启停，不做新增/改密/改角色”的边界。
- 是否接受申请人下拉展示全部启用 `Applicant` 用户，并支持关键字搜索，而非仅展示已有报销用户。
