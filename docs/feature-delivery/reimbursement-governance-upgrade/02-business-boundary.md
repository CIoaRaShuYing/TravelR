# 报销治理升级：业务边界

## 核心业务对象

| 对象 | 责任与归属 |
| --- | --- |
| 项目 | 由管理员创建、修改和停用；历史上已被报销引用的项目不得物理删除。 |
| 用户 | 申请人归属现有 Identity 账户；一个用户可在多个项目下提交多笔报销。 |
| 报销主记录 | 稳定保存报销单号、申请人、当前项目、当前有效版本、删除状态和发放状态。 |
| 报销版本 | 保存某次编辑后的不可变快照，包括项目、说明、行程、费用、附件和金额；旧版本只读。 |
| 审批记录 | 必须指向具体报销版本，记录批准/驳回、意见、操作者和时间。 |
| 发放记录 | 独立于审批记录，记录待发放变为已发放时的管理员、时间和备注。 |
| 注册申请 | 保留现有待审核、已批准、已拒绝状态，由管理员页面处理。 |

## “项目—人员—报销”关系

```text
项目 1 ---- N 报销主记录 N ---- 1 申请人
                    |
                    1
                    |
                    N 报销版本 ---- 审批记录
                    |
                    └---- 行程 / 费用条目 / 私有附件
```

一笔报销只能属于一个项目和一个申请人。管理员汇总以报销主记录为入口，可按项目分组后再按人员分组，也可反向按人员分组后再看项目。无需为“项目—人员—报销”额外制造重复数据。

## 报销与版本状态机

```text
新建 -> Draft(v1) -> Submitted(v1) -> Approved(v1) -> PendingPayout -> Paid
          |               |
          | 编辑          | 编辑/删除（批准前）
          v               v
       Draft(v2)       Draft(v2) / Cancelled
       v1=Superseded   v1=Superseded

Submitted -> Rejected -> 编辑生成 Draft(v2) -> 再提交
```

规则：

- 每次成功保存修改都创建新版本；上一版本标记为 `Superseded`，内容保持只读。
- 编辑已提交版本时，原待审批任务立即失效，新版本回到草稿；用户必须明确再次提交。
- 删除未批准报销时标记为 `Cancelled`，不物理删除版本、审批记录和附件。
- 审批接口只能批准“报销主记录当前指向、且状态为 Submitted”的版本；旧页面对旧版本发起批准必须返回冲突并提示刷新。
- `Approved` 后用户不能再编辑或删除。
- 批准后发放状态独立变为 `PendingPayout`；管理员确认后变为 `Paid`。

## 权限边界

| 操作 | 申请人 | 管理员 |
| --- | --- | --- |
| 查看自己的报销 | 是 | 是 |
| 新建、保存、提交 | 自己 | 管理员作为申请人时可操作自己的 |
| 批准前编辑/作废 | 自己 | 不代替用户修改 |
| 批准/驳回 | 否 | 是 |
| 确认已发放 | 否 | 是 |
| 创建/停用项目 | 否 | 是 |
| 注册申请审批 | 否 | 是 |
| 查看全部报销汇总 | 否 | 是 |

## 数据流与一致性边界

1. 用户选择启用项目并创建报销主记录和 v1 草稿。
2. 保存修改时，在一个数据库事务中创建新版本、复制/关联有效附件、切换当前版本并作废旧版本。
3. 提交时只提交当前版本。
4. 审核时校验当前版本标识和提交状态，防止批准过期版本。
5. 批准后生成待发放状态；发放确认另写发放记录和审计日志。
6. 所有汇总默认只统计当前有效版本，历史版本只在详情和审计页查看，避免金额重复。

补充规则：

- 管理员同时拥有申请人身份时，可以提交并审批自己的报销；因为系统不再设置独立审核人，禁止自审会使单管理员部署无法完成流程。所有自审动作必须完整记录审计。
- 项目停用后不再出现在新报销的项目选项中；已经引用该项目的在途报销可以继续保留原项目、提交和审批，但编辑时不能切换到其他停用项目，避免停用操作使全部在途草稿失效。
- 管理员汇总中的日期筛选首期明确为报销创建日期，费用发生日期不与该口径混用。

## 首期明确不做

- 不做银行自动付款、ERP/财务系统同步、预算占用和会计凭证生成。
- 不做多级会签或按金额动态审批链。
- 不做 OCR、发票验真和自动查重。
- 数据库重建完成后，新产生的业务报销、旧版本、审批记录或发放记录不允许物理删除。

## 数据库重建边界

- 用户已授权在实施阶段清空当前数据库，删除现有用户、项目、报销、审批、发放和审计数据，并按新模型重新创建。
- 不编写旧报销到新版本模型的数据迁移，不创建历史兜底项目。
- 数据库清空仅在对应实施里程碑执行；执行前仍需解析并核对目标连接字符串，禁止对未确认目标使用删除命令。
- 重建后重新执行迁移、角色种子和首位管理员初始化流程；私有附件存储是否同步清空必须与数据库同批次处理，避免遗留无主文件。

## 本地附件存储边界

- 本地私有目录是唯一附件存储，不再运行或依赖 MinIO/S3 服务。
- 数据库只保存附件元数据和相对对象键；物理文件保存在配置的 `FileStorage:LocalPath` 下。
- 本地目录不得位于 `wwwroot`，不得由 Nginx 直接公开；上传和下载继续经过现有 JWT 与对象归属鉴权。
- 单机单 API 实例是当前部署边界；未来若需要多实例或跨主机共享存储，必须重新评估共享文件系统或对象存储，不能让多个实例各写本机目录。
- 数据库和附件目录必须作为同一业务快照备份、恢复；只恢复一侧会产生缺失文件或无主文件。
