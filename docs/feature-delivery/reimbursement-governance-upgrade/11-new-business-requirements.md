# 报销治理升级：餐补、月度导出、周报与收款资料需求

## 1. 范围与现状约束

本文件是现有报销治理功能的新增需求扩展，当前只完成需求整理，不修改生产代码。现有系统以 `ReimbursementClaim -> ClaimVersion -> TravelItinerary` 保存报销和行程，已有报销审核、发放确认、项目管理、用户管理和 `AuditLog`。当前行程只有出发日和返程日，没有时分字段；当前用户只有注册显示名称，没有独立个人姓名和银行卡字段；系统不直连银行。

本轮需求口径已于 2026-08-10 确认：行程按日期计算；每次差旅报销自动同步申请餐补，不提供用户选择项，并由管理员顺序审核两次；保留审核与发放两步；导出按费用提交时间；周报无审核且用户、管理员均可编辑；银行卡未填写时禁止进入其他业务页面；管理员直接查看完整卡号并可一键复制。

## 2. 差旅餐补自动申请与发放

### 业务规则

- 每次新建差旅报销时，系统必须自动同步创建餐补子记录；用户界面不提供“是否申请餐补”的开关、复选框或独立申请入口。
- 保存差旅草稿时同步保存餐补草稿，提交差旅报销时两者在同一事务中一起进入待审核；任一记录保存失败时整次操作回滚。
- 项目、申请人、行程起止日期自动取自差旅报销当前版本，禁止手工修改餐补天数。
- 按自然日含首尾计算：`餐补天数 = 返程日期 - 出发日期 + 1`。当天往返为 1 天，返程日期早于出发日期不可提交，不引入时分字段和按小时折算规则。
- 餐补是差旅报销下的独立子记录，保存 `ClaimId`、`ClaimVersionId`、项目快照、申请人、起止日期快照、天数和独立状态，不改写原报销费用总额。
- 同一差旅报销版本最多关联一份餐补申请，不允许拆分多次申请。差旅报销被修改并生成新版本时，餐补信息随新版本重新保存和提交。

### 申请人功能

- 用户只填写差旅报销及行程，不需要填写或确认“申请餐补”；系统自动展示根据行程日期计算的餐补天数预览。
- 餐补与差旅报销同步保存草稿、同步提交，用户不能单独撤回、删除或重复提交餐补。
- 查看项目、报销单号、行程、天数、日标准、计算总额、审核意见、发放状态和处理时间。
- 只可编辑草稿或被驳回的差旅报销及其餐补；提交后锁定来源行程和计算快照。

### 管理员功能

- 管理员在同一差旅报销详情中执行两次独立审核：第一次审核差旅报销，第二次审核该差旅自动生成的餐补。两次审核分别形成审批记录，不能用一次确认同时批准两项。
- 差旅报销未审核通过前，餐补日标准输入和餐补审核按钮保持禁用；差旅报销审核通过后也不会自动批准餐补。
- 差旅报销被驳回时，其餐补在同一事务中自动驳回并使用同一驳回原因，不要求管理员再执行第二次驳回，也不允许继续审核餐补。
- 差旅报销审核通过后，餐补才进入可审核状态。管理员在第二次审核中必填每日发放金额（正数、精确到 0.01 元），系统计算 `餐补总额 = 天数 × 每日金额`，明确展示天数、日标准和总额。
- 管理员点击“确认金额并审核通过”后，事务性保存餐补金额快照、审核人、审核时间和备注，餐补进入待发放状态。金额确认后不可静默修改。
- 差旅报销与餐补均保留“审核通过 -> 待发放 -> 已发放”两步流程，分别记录发放金额和状态，不能因确认其中一项而隐式确认另一项。
- 餐补发放确认时展示申请人个人姓名和完整银行卡号，记录发放人、时间、金额、收款人姓名和银行卡后四位。该操作表示线下或外部财务已完成发放，不代表系统已完成银行转账。
- 驳回、联动驳回、金额确认、发放确认均写入审批记录和审计日志；日志不得包含完整银行卡号。

### 补充规则

- 所有差旅报销都自动带有餐补审核步骤；普通单据报销不生成餐补，也不出现餐补审核步骤。
- 差旅报销通过、餐补被单独驳回时，不回退已经通过的差旅报销；申请人只能随新的差旅报销版本重新提交餐补。
- 每日金额本期不设置统一上限或项目级标准，只校验大于 0 且精确到分；后续如增加标准配置，需另行确认。

## 3. 每月按项目导出报销

- 仅管理员可用，必须选择项目；可选费用提交日期区间，停用项目仍可查询历史数据。
- 日期归属固定使用报销的费用提交时间 `SubmittedAt`，不按费用发生日、审核日或发放日归属。
- 未选择日期区间时，默认起始日为上月 10 日、结束日为本月 10 日，界面按自然日含首尾展示；服务端查询使用 `[上月10日 00:00:00, 本月11日 00:00:00)`，以包含本月 10 日全天，时区使用 `Asia/Shanghai`。
- 用户手工选择日期区间时同样包含起止日期全天；结束日期通过“小于结束日次日零点”实现，避免遗漏当日记录。
- 导出范围包括区间内提交的已提交、已批准、已驳回和已作废记录，排除草稿；每张报销单只导出查询口径下的有效版本，避免版本重复。
- 默认输出 `.zip` 压缩包；压缩包根目录包含一份 `.xlsx`，内容继续包括报销单汇总、费用明细、行程明细和餐补明细，餐补单独合计且不能重复计入原报销金额。
- Excel 的“报销汇总”工作表末尾必须增加“总计”行，显示本次导出笔数和报销金额合计；餐补金额保持独立，不并入该报销总计。
- 压缩包根目录包含 `报销凭证/` 文件夹，收录本次查询范围内每张报销单当前有效版本所关联的全部费用凭证；没有凭证时仍保留空文件夹。
- 凭证文件名使用 `个人姓名_金额.原扩展名`：个人姓名取申请人填写的 `PersonalName`，金额取凭证所属费用明细金额并固定保留两位小数；文件名非法字符替换为 `_`。
- 同一用户名、同一金额出现多个凭证时，为避免 ZIP 内文件覆盖，从第二个文件开始追加 `_2`、`_3` 等序号；凭证保留原扩展名，不保留原始文件名。
- 数据库存在凭证记录但私有存储中的实体文件缺失或不可读时，整个导出失败并返回明确错误，不生成缺少凭证的“成功”压缩包。
- 汇总字段至少包括报销单号、申请人、项目编码/名称快照、报销类型、状态、发放状态、报销金额、提交/审核/发放时间；费用和行程表通过报销单号关联。
- Excel 和文件名均不包含完整银行卡号、密码、JWT 或其他鉴权信息；凭证二进制只存在于 `报销凭证/` 文件夹，不嵌入 Excel。无数据时仍返回包含带表头 Excel 和空凭证文件夹的压缩包。
- 后端按完整查询生成，不受列表分页影响；记录导出人、项目、实际起止日期、生成时间、行数和结果状态。

## 4. 项目周报

- 用户创建周报时必须选择一个启用项目和周区间；沿用现有规则，所有用户均可选择全部启用项目。按中国时区以周一至周日为一个自然周。
- 每个用户、项目、周只能有一份周报；重复创建时打开已有记录而非新增重复数据。
- 字段固定为：本周完成情况（必填）、下周计划（必填）、问题/需协助事项（可选）。本期不增加工时、里程碑和附件。
- 周报不设草稿、提交、审核、驳回或发放状态；首次保存即形成有效周报，后续可持续编辑。
- 用户可查看和编辑本人周报；管理员可查看和编辑所有用户周报。普通用户不能编辑他人周报。
- 每次保存记录创建人、最后编辑人、创建时间、更新时间，并写入审计，管理员编辑不改变周报原作者。
- 用户按项目和周查看本人历史；管理员按项目、用户和周查看/汇总。周报不提供审核流程，不自动参与报销或餐补计算。

## 5. 个人姓名与银行卡

- 用户中心新增个人姓名和银行卡号编辑；用户只能维护本人，管理员只读查看。
- 银行卡校验 16-19 位数字，姓名去除首尾空格并进行长度校验；本期不使用 Luhn 作为强制校验，避免合法卡号被误拒。
- 登录成功后服务端返回资料完整性标记。银行卡号未填写时，前端必须直接跳转个人资料填写页，禁止进入其他业务页面；页面明确说明“报销及餐补发放将使用此银行卡信息”。
- 个人资料页要求同时填写个人姓名和银行卡号才能完成；除个人资料读取/保存、修改密码和退出登录外，其余受保护业务接口也必须拒绝资料不完整用户，防止绕过前端直接进入系统。
- 资料补全后立即解除门禁并进入系统；后续清空银行卡号不被允许。发放确认前服务端再次校验个人姓名和银行卡号完整。
- 管理员用户管理页面直接显示完整银行卡号，不做脱敏，不要求二次展示确认；卡号旁提供“一键复制”图标按钮，复制成功后显示明确提示。
- 管理员可读取所有正式用户的完整银行卡号；普通用户只能读取本人，未授权接口返回 403。管理员查看用户列表/详情和复制卡号均写入审计，但审计内容不得保存卡号原文。
- 完整卡号不得进入 JWT、报销/月度导出、日志、异常响应或前端调试输出；数据库须加密存储或采用等价密钥保护。管理员专用用户查询响应因业务要求允许返回完整卡号。
- 发放确认保存收款人姓名和银行卡后四位快照，用户后续修改资料不改变历史记录；本期不在历史发放记录中重复保存完整卡号。
