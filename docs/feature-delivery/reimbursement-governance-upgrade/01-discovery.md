# 报销治理升级：现状调研

## 架构摘要

- 前端：Vue 3、TypeScript、Vite、Element Plus，当前主要业务集中在 `frontend/src/App.vue`。
- 后端：ASP.NET Core 8 Minimal API、EF Core、ASP.NET Core Identity。
- 数据：PostgreSQL 保存账户、报销、审批、审计和附件元数据；附件存储原先同时保留本地与 MinIO 两套实现。
- 角色：`Applicant`、`Reviewer`、`Administrator`。

## 已确认事实

### 1. 注册审批后端已存在，前端未接入

- `Program.cs:214-256` 已实现注册申请列表、批准和拒绝接口。
- `App.vue:192-215` 的管理员入口只有“管理设置”，内容只有注册策略，没有注册申请列表和操作按钮。
- `frontend/src/api.ts` 也没有注册申请列表、批准、拒绝方法。

结论：这不是从零新增注册审批后端，而是先补齐管理页面和前端 API，再完善分页、状态筛选和处理结果展示。

### 2. 当前报销模型没有项目、版本和发放概念

- `Entities.cs:41-58` 的 `ReimbursementClaim` 只包含申请人、类型、说明、单一审批状态、金额和时间。
- `ClaimStatus` 只有 `Draft`、`Submitted`、`Approved`、`Rejected`。
- 当前没有 `Project`、版本链、作废状态、发放状态或发放记录实体。

结论：项目归属、修改作废和发放确认均需贯穿数据库、领域模型、API、权限和页面。

### 3. “草稿不能编辑”主要是前端闭环缺失

- 后端 `PUT /api/claims/{id}` 允许编辑 `Draft` 或 `Rejected`，但直接原地覆盖当前报销及费用条目。
- 前端 `saveClaim` 在保存数据和附件后立即调用提交接口，没有“仅保存草稿”的独立动作。
- “我的报销”只为 `Rejected` 显示“继续编辑”，`Draft` 没有编辑按钮，也没有删除按钮。
- 后端没有报销删除/撤回接口。

结论：需要同时改交互、API 和数据模型；只补两个按钮不能解决管理员审批旧数据的并发一致性问题。

### 4. 审核工作台不是全量汇总

- `GET /api/review/claims` 只返回 `Submitted` 状态。
- 页面只显示待审核报销，没有项目、审批状态、发放状态、日期区间、用户筛选、分组和分页。
- `GET /api/claims` 只返回当前用户数据，也不支持项目筛选。

## 关键风险

1. 如果继续原地更新报销，管理员打开旧内容后可能批准用户刚修改过的新内容，或批准已被用户撤回的内容。
2. 如果“删除”执行物理删除，审批记录、附件归属和审计链会断裂。
3. 如果发放状态复用审批状态，会把“业务认可”和“财务已付款”混成一个状态，无法准确汇总。
4. 如果项目可以硬删除，历史报销会失去归属；项目应停用而不是删除有业务数据的记录。
5. 管理员汇总若一次返回全部数据，数据增长后不可用；必须服务端分页、筛选和汇总。

## 推荐扩展点

- 在现有管理员授权组下扩展注册申请、项目和报销汇总 API。
- 将当前报销行作为“版本数据”迁移，并增加稳定的报销主记录指向当前版本。
- 让审批记录明确关联被审批的版本。
- 将发放状态与发放操作记录独立建模。
- 前端将“管理设置”“注册审批”“项目管理”“报销汇总”分成独立功能页面。

## 2026-08-03 本地存储收敛调研

- 开发配置已选择 `Local`，但路径硬编码为 API 内容根下的 `private-uploads`；该历史目录属于另一 Windows 运行账户，实际上传在 `File.Create` 处返回 `UnauthorizedAccessException`。
- Compose 仍强制启动 MinIO，后端仍引用 MinIO SDK，导致开发与部署采用不同存储路线。
- `IPrivateFileStore` 的保存、鉴权读取、补偿删除和过期暂存清理边界已经适合本地文件，不需要修改附件业务模型或 API 合同。
- 当前单文件上限为 10MB，目标是单机轻量部署；直接文件系统 I/O 足够，不需要对象存储服务。
- 推荐将存储根目录配置化到工作区/容器独立数据目录，并在启动阶段验证可写性；Compose 使用持久卷而不是容器可写层。
