# 报销治理升级：需求接收

## 用户原始目标

当前系统缺少可用的管理员注册审批界面、项目维度、草稿编辑删除、修改后的版本一致性、报销发放状态、管理员全量汇总和项目筛选，需要补齐为可实际使用的报销管理闭环。

## 推断出的业务目标

1. 管理员能够真正处理待审核注册申请，而不只是切换注册策略。
2. 报销必须归属管理员创建的项目，形成“项目 -> 人员 -> 报销”的查询与汇总结构。
3. 用户在报销批准前可以编辑或删除；任何已保存版本被修改后都不能继续被管理员批准。
4. 报销审批状态和发放状态分离，批准后由管理员确认是否已经发放。
5. 管理员能查看全部报销，用户和管理员均可按项目筛选，管理员还能按用户分组。

## 本轮范围

- 只读核查现有前端、API、实体、权限和数据库映射。
- 建立业务边界、需求草案和验收标准。
- 提交需求级改造方案供确认。
- 本轮不修改生产代码、不生成数据库迁移、不进入实现任务拆解。

## 已知约束

- 保留现有私有附件能力。
- 业务角色简化为 `Applicant` 和 `Administrator`；不再保留独立 `Reviewer` 职责，管理员负责注册审批、报销审批、项目管理、发放确认和全量汇总。
- 保留现有 `Travel`、`General` 两种报销类型。
- 旧版本、审批记录和附件不能因用户“删除”或“修改”而物理清除，否则无法审计，也无法证明管理员批准的是哪一版数据。
- 报销批准后禁止普通用户继续编辑或删除。
- 用户已明确授权清空现有数据库并按新模型重建，不要求迁移或保留当前数据库中的业务数据。

## 已确认决策（2026-08-03）

- 所有启用中的项目对全部申请人开放选择，不维护项目成员名单。
- 用户删除未批准报销采用“作废/撤回”而不是物理删除。
- 管理员统一负责注册审批、报销审批、项目管理、发放确认和汇总，不设置独立审核人业务角色。
- 发放状态首期为“无需发放/待发放/已发放”，不对接银行或财务系统；“已发放”不可直接撤销。
- 数据库执行破坏式清空和重建，不创建“历史未归属项目”，不迁移现有报销。

## 需求确认结果

- 用户已确认业务边界、需求方向和以上四项决策。
- 需求确认闸口已通过，可以进入只读技术分析、技术设计和任务拆解。
- 原始请求是整理改造方案，因此在技术方案和任务清单完成后停止，不自动执行生产代码改造或数据库清空。

## 补充确认：本地附件存储（2026-08-03）

- 用户确认正式移除 MinIO，将本地私有目录作为唯一附件存储。
- 单机轻量部署是当前边界；不要求多个 API 实例共享附件目录。
- 附件仍必须经鉴权 API 上传和下载，不暴露为静态目录。
- PostgreSQL 附件元数据与本地附件目录必须同批次备份和恢复。
- 用户已确认该部署架构调整，可以直接进入实现和验收。
