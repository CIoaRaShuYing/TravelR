# 报销治理升级：技术分析

## 分析方式

用户已明确允许启用只读子代理。本阶段由两个子代理分别分析后端/数据库和前端/交互，主 Agent 负责复核并形成最终判断。全部分析均为只读，没有修改生产代码、数据库或附件。

## 当前实现事实

### 后端与数据

- `ReimbursementClaim` 同时承载内容和审批状态，行程、费用、附件直接挂载其下；没有项目、版本、当前版本指针、发放状态或并发令牌：`Domain/Entities.cs:41-108`。
- 更新接口原地覆盖报销内容，只允许 `Draft`、`Rejected`；旧内容不保留：`Program.cs:288-359`。
- 审批采用读取状态后直接 `SaveChanges`，请求中没有被审核的版本标识：`Program.cs:410-433`。
- 现有请求 DTO 没有 `ProjectId`、`ExpectedCurrentVersionId` 或并发戳：`Contracts/Requests.cs:14-19`。
- 注册申请查询/批准/拒绝接口已经存在，但查询只 `Take(100)`，没有分页元数据：`Program.cs:214-256`。
- 角色种子和授权仍依赖 `Reviewer`：`Program.cs:403`、`Program.cs:448-464`、`Program.cs:509-513`。
- 管理员初始化仍使用 `BootstrapAdmin:Email`，但登录只按手机号用户名查询，环境初始化账户可能无法登录：`Program.cs:177-186`、`Program.cs:453-464`。
- 附件存储接口只有保存和读取；对象写入成功后如果数据库保存失败，会留下无主对象：`Services/PrivateFileStore.cs:8-12`、`Program.cs:380-392`。
- 应用启动会自动执行迁移，现有迁移属于旧单表模型：`Program.cs:438-452`、`Data/Migrations/`。

### 前端与交互

- 所有视图、状态、请求和模板集中在单一 `App.vue`，目前靠 `view` 字符串切换五个视图：`frontend/src/App.vue:7-22`、`frontend/src/App.vue:151-215`。
- 注册审批后端接口没有接入 `frontend/src/api.ts`，管理设置页只有注册策略。
- 当前保存流程是“更新 -> 上传附件 -> 立即提交”，没有独立保存草稿：`App.vue:82-101`。
- 保存前强制全部字段和附件完整，无法保存不完整草稿：`App.vue:84-86`。
- 只有 `Rejected` 显示编辑入口，所有状态均没有删除/撤回：`App.vue:124-136`、`App.vue:207`。
- 前端仍判断并展示 `Reviewer`；列表 DTO 使用宽泛字符串和 `unknown[]`，管理员列表复用错误的 `Claim` 类型：`App.vue:24-25`、`frontend/src/api.ts:3-4`。
- 我的报销和审核工作台一次返回全部数组，没有服务端分页、筛选、分组、总数或总金额。
- 已有附件被简化成 `hasAttachment`，无法查看文件名、下载、移除或替换。

## 根因判断

1. 现有实现把“报销业务身份”“当前内容”“审批状态”放在同一行，原地更新无法证明管理员批准的是哪一版。
2. 只给 `Submitted` 增加编辑按钮会产生竞态：管理员打开 v1，用户保存 v2，旧审批请求仍可能批准当前行。
3. 当前附件归属于具体费用条目，复制新版本时要么丢失旧附件，要么复制实际文件，均不合理。
4. 审批状态与发放状态属于两个不同业务事实；复用一个枚举会让汇总口径错误。
5. 前端继续向单一 `App.vue` 增加管理页面会导致权限、加载状态和表单状态互相污染。

## 选择的技术路线

### 报销主记录与版本分离

- `ReimbursementClaim` 改为稳定主记录：单号、申请人、当前版本指针、当前审批状态、独立发放状态、并发戳。
- 新增 `ClaimVersion`：项目、说明、行程、费用和金额快照；每次保存新建一行。
- 旧版本填写 `SupersededAt`，只能查看；当前有效性以 `ReimbursementClaim.CurrentVersionId` 为唯一裁决。
- 审批和发放均同时校验 `expectedCurrentVersionId` 与并发戳，冲突返回 HTTP 409。

### 附件资产化

- 文件先上传为申请人名下的不可变 `AttachmentAsset`，再通过 `ExpenseItemAttachment` 关联到版本费用条目。
- 新版本复用同一个附件资产，不复制实际对象；移除附件只影响新版本关联，旧版本仍可查看。
- 存储接口增加内部 `DeleteAsync`，用于上传补偿、过期临时附件清理和经确认的破坏式重建，不暴露清空桶 HTTP API。

### 管理员统一职责

- 只保留 `Applicant`、`Administrator` 两个业务角色。
- 注册审批、项目、报销审批、发放和汇总统一进入 `/api/admin` 权限边界。
- 管理员仍具有申请人身份，允许自审并完整记录审计。

### 前端模块化

- 引入官方 `vue-router` 处理申请人和管理员页面，不引入 Pinia；会话保持轻量组合函数。
- `App.vue` 只保留应用壳、会话初始化和路由出口。
- 管理员报销管理采用“待审批 / 待发放 / 全部报销”三个标签，共用筛选和详情组件。

## 并发与安全边界

- 报销主记录增加应用级 Guid 并发戳；每次版本切换、提交、撤回、审批和发放均轮换。
- 保存、提交、撤回、审批和发放必须在单个 PostgreSQL 事务中完成状态、记录和审计写入。
- `DbUpdateConcurrencyException`、版本不匹配和状态冲突统一转换为 409，不自动重试业务冲突。
- JWT 验证阶段增加用户仍存在且 `IsActive=true` 的检查，使数据库清空后的旧令牌失效；不依赖仅轮换密钥解决。
- `BootstrapAdmin` 改用手机号。Compose 部署必须在公开服务前完成管理员初始化；开发环境可保留现有首位管理员引导。
- 不在应用启动时加入自动清库逻辑。

## 破坏式重建判断

- 用户已经明确授权放弃当前数据库和附件数据，因此不编写兼容迁移，不创建历史兜底项目。
- 最简单可靠的路线是移除旧业务迁移，按新模型生成单一基线迁移。
- 真正清理必须在新代码和基线迁移已通过临时空库验证之后进行。
- 数据库和附件存储必须同批次清理；当前工作区存在根目录和 API 目录两处本地附件历史，Docker 模式另有 MinIO 桶，执行时必须根据最终生效配置解析精确目标。
- 清理后旧数据不可恢复；回滚只代表重新部署旧代码/重建空旧结构，不恢复原业务数据。

## 不采用的方案

- 不采用原表加一个 `VersionNumber` 后继续原地覆盖：不能保存子表快照。
- 不采用整单 JSON 快照：不利于项目筛选、金额汇总、外键和附件权限。
- 不复制实际附件文件到每个版本：造成存储放大。
- 不使用 Redis/分布式锁：单 PostgreSQL 下版本 ID、并发戳、事务和唯一约束足够。
- 不让浏览器加载全部报销后本地分组：分页和汇总口径会失真。
- 不继续堆叠单一 `App.vue`，也不引入 Pinia、微服务或银行支付集成。

## 2026-08-03 MinIO 移除分析

### 当前事实

- `appsettings.json` 已配置本地存储，但 `LocalPrivateFileStore` 把目录硬编码到 API 内容根；真实上传因该历史目录不可写而返回 500。
- Compose、MinIO SDK 和 `MinioPrivateFileStore` 仍构成第二条部署路线，增加一个容器、一个数据卷和一组密钥。
- 附件上限 10MB，保存接口采用流式写入并同步计算 SHA-256；单机本地磁盘不需要经过额外 HTTP 对象存储层。

### 技术判断

- 保留 `IPrivateFileStore`，因为它隔离业务层与文件系统，并承载补偿删除和后台清理；只删除 MinIO 实现，不把文件操作散回 Endpoint。
- `FileStorage:LocalPath` 支持绝对路径和相对内容根路径；开发环境指向仓库根 `private-uploads`，容器环境指向持久卷 `/data/private-uploads`。
- 服务构造时创建目录并执行临时写探针，目录不可写时让主机启动失败，避免首个用户上传才看到通用 500。
- 使用 `Path.GetRelativePath` 校验对象键，防止前缀比较导致的相邻目录逃逸。
- 不迁移 MinIO 对象：切换前确认当前 MinIO 无业务桶和对象；只移除精确的 `chuchai-minio-1` 和 `chuchai_minio_data`。

## 主要风险

1. 对象存储和 PostgreSQL 无法组成同一事务，必须有补偿删除和临时附件清理。
2. 破坏式清理目标如果解析错误会删除错误数据库或桶，必须在执行前展示脱敏目标并精确核对。
3. 用户修改和管理员审批并发是最高业务风险，必须有真实 PostgreSQL 并发测试，不能只靠前端按钮隐藏。
4. JWT 若只保存在模块内存中会导致刷新丢失；M7 已改为当前标签页 `sessionStorage` 恢复，并在过期、401 和主动退出时清理，不扩大为 Cookie 或长期 `localStorage` 会话。
