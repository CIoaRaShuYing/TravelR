# 报销与餐补看板：需求说明

## REQ-001

- 优先级：Must
- 业务目的：将页面定位从“详情列表”明确为“餐补看板”。
- 影响角色：Administrator。
- 输入：访问现有餐补页面或导航。
- 输出：导航、路由标题和页面标题统一显示“餐补看板”。
- 涉及模块：`AppShell.vue`、`router.ts`、`AdminMealAllowancesView.vue`、相关交付文档。
- 默认假设：保留 `/admin/meal-allowances` 和 `/api/admin/meal-allowances`。
- 依赖事项：现有餐补看板功能。
- 不做事项：不创建兼容跳转或更换 API。

## REQ-002

- 优先级：Must
- 业务目的：按单条费用明细查看当前报销数据。
- 影响角色：Administrator。
- 输入：访问 `/admin/reimbursement-dashboard`。
- 输出：每条当前版本 `ExpenseItem` 独立一行，包含申请人、项目、报销号/版本、类别、费用日期、金额、商户、备注、报销状态和更新时间。
- 涉及模块：管理员 API、前端 API 类型、新页面、路由和导航。
- 默认假设：只包含 `Submitted`、`Approved`、`Rejected`；排除 `Draft`、`Cancelled` 和餐补。
- 依赖事项：`ReimbursementClaim.CurrentVersionId`、`ClaimVersion.ExpenseItems`。
- 不做事项：不展示旧版本费用为独立行，不提供写操作。

## REQ-003

- 优先级：Must
- 业务目的：按业务维度定位费用明细。
- 影响角色：Administrator。
- 输入：费用类别、费用日期范围、项目、申请人。
- 输出：条件可单独或组合生效；清空条件恢复全部；分页不丢失筛选。
- 涉及模块：费用明细查询、新页面筛选区。
- 默认假设：日期按 `ExpenseDate` 闭区间判断；类别筛选提供六个可提交业务类别，不提供 `Unspecified`。
- 依赖事项：现有项目和申请人目录 API。
- 不做事项：本轮不新增报销状态筛选。

## REQ-004

- 优先级：Must
- 业务目的：在餐补和费用两个看板复用有效的划分方式。
- 影响角色：Administrator。
- 输入：餐补看板选择“按项目”或“按人员”；报销看板选择“按项目”“按人员”或“按类别”。
- 输出：当前看板按选定维度返回完整筛选集的分组卡片；点击卡片设置或取消相应筛选。
- 涉及模块：餐补/费用分组 API、两个看板页面、共用样式。
- 默认假设：报销看板的类别分组使用 `ExpenseCategory` 稳定值和中文标签；切换维度后保留其他筛选并刷新分组。
- 依赖事项：`AdminClaimsView.vue` 现有交互模式。
- 不做事项：餐补看板不增加类别维度；报销看板的类别仍可同时作为筛选条件。

## REQ-005

- 优先级：Should
- 业务目的：快速理解当前筛选范围的数据规模。
- 影响角色：Administrator。
- 输入：当前看板筛选条件。
- 输出：报销看板显示费用明细数、已填写金额、金额待填写数；餐补看板保留餐补数、已核定金额、待核定数。
- 涉及模块：管理员聚合 API、两个看板汇总带。
- 默认假设：空金额按 0 汇总，聚合不受分页影响。
- 依赖事项：服务端聚合查询。
- 不做事项：不新增图表、趋势分析或导出。

## REQ-006

- 优先级：Must
- 业务目的：从明细追溯报销上下文。
- 影响角色：Administrator。
- 输入：点击报销看板费用明细或餐补分组后的明细。
- 输出：打开现有 `ClaimDetailDrawer` 查看关联报销。
- 涉及模块：两个看板、`ClaimDetailDrawer.vue`。
- 默认假设：详情包含既有版本审计信息。
- 依赖事项：现有报销详情 API。
- 不做事项：不复制详情组件。
