# 工资发放管理：只读技术分析

## 分析方式

用户已确认启用只读子代理。后端、前端、数据库与安全三路分析均只读取文件，未修改代码；主 Agent 复核后形成以下结论。

## 已验证事实

- 后端为 ASP.NET Core 8 Minimal API、EF Core、Npgsql，管理接口统一挂在 `Administrator` 路由组。
- `AppUser` 已有个人姓名与受 Data Protection 保护的银行卡号；报销和餐补发放会在事务内校验状态、保存卡号尾号快照、生成唯一发放记录并写审计。
- 现有并发模式为业务 `Guid ConcurrencyToken` 加 EF `IsConcurrencyToken()`，冲突返回 409。
- 前端使用 Vue 3、Element Plus、集中式 `api.ts` 和静态路由，没有 Pinia 或额外请求库。
- 现有 XLSX writer 可安全复用，不需增加 Office 依赖。

## 技术判断

- 新增 `PayrollPeriod`、`PayrollEntry`、`PayrollPayoutRecord`，不修改 `AppUser` 的账号职责，不关联报销或餐补表。
- `PayrollPeriod` 是聚合并发根；增删人员、保存、锁定、退回、取消和逐人发放都校验并刷新期间令牌。
- 明细同时持有自己的并发令牌；批量保存先全部校验再一次提交，任一冲突则全批失败。
- 历史展示使用工资明细快照，不实时拼接当前用户姓名。
- 完整银行卡只在服务端锁定/发放时短暂解密；工资 JSON、审计和 Excel 均不得包含完整卡号。
- “部分发放”由已发/待发人数及金额派生，不落成可手工修改的期间状态。

## 风险与处理

- 当前 `/api/admin/users` 会返回完整银行卡号，工资候选人必须使用独立投影。
- `Program.cs` 已较集中，工资业务逻辑必须放入独立服务，路由只编排授权和请求。
- 前端工资列较多：桌面使用横向可滚动表格，移动端使用卡片和编辑对话框。
- 当前 Data Protection key ring 未显式持久化；直接新增空密钥卷可能导致已有银行卡密文无法解密。本功能代码不执行生产密钥迁移，上线前需单独完成旧密钥保全和容器重建解密验证。
- 基线构建在普通权限下因既有 `obj`、`.tmp` 和 `node_modules/.tmp` ACL 报错；验证时需使用已授权的可写/提升权限路径，不能误判为功能失败。
