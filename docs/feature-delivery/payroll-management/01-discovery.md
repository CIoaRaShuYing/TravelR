# 工资发放管理：现状调研

## 项目架构摘要

- 后端为 ASP.NET Core 8 Minimal API、EF Core 和 PostgreSQL，入口集中在 `backend/TravelReimbursement.Api/Program.cs`。
- 核心实体集中在 `backend/TravelReimbursement.Api/Domain/Entities.cs`，映射集中在 `Data/AppDbContext.cs`，迁移由应用启动时自动执行。
- 前端为 Vue 3、TypeScript、Element Plus；路由位于 `frontend/src/router.ts`，接口封装集中在 `frontend/src/api.ts`。
- 管理员页面和普通用户页面共用一个前端应用，由路由元数据和 `Administrator` 角色控制管理端访问。

## 可复用的现有能力

- 正式用户目录：`GET /api/admin/users` 可查询启用和停用的正式用户；`GET /api/admin/applicants` 只返回启用的 `Applicant` 用户。
- 收款资料：`AppUser` 已有 `PersonalName` 和 `BankCardProtected`；管理员读取或复制银行卡信息时已有审计。
- 发放模式：报销与餐补采用 `Pending -> Paid`，在数据库事务中校验状态和并发令牌，并生成一对一不可变发放记录。
- 审计模式：`AuditLog` 保存操作者、动作、对象、上下文、TraceId 和时间。
- 金额模型：现有金额统一使用 PostgreSQL/EF Core `decimal(18,2)` 精度。
- 前端体验：现有管理页面已经包含人员选择、筛选、分页、状态标签、桌面表格和移动端列表模式。

## 当前不存在的能力

- 没有工资月份、工资明细、工资发放凭证或工资导出模型。
- 没有员工在职状态、入离职日期、部门、岗位、工资标准等人事主数据。
- 没有工资审批、复核、真实银行转账或银行回执同步。
- 没有针对工资数据的独立角色；现有管理员默认拥有全部管理权限。

## 关键扩展点

- 在新领域服务中复用现有收款资料校验、卡号尾号快照、事务、并发令牌和审计模式。
- 使用独立工资期间和工资明细实体，不把工资字段直接加到 `AppUser`，避免把登录账号状态误作劳动关系。
- 新增管理员工资管理页；如果确认普通用户自助查看，则新增“我的工资”页。
- 使用独立迁移新增工资表，不改写现有报销和餐补表。

## 关键风险

- 工资属于高敏感数据，不能复用返回全量银行卡号的普通列表响应作为工资列表数据。
- 如果按当前启用用户实时查询历史月份，用户停用、改名或改卡后会改变历史工资表，因此必须保存月度人员与收款快照。
- 如果实发金额由前端计算并直接提交，公式可能被绕过；最终金额必须由服务端计算和校验。
- 如果整月一次性标记已发放，任何单人资料缺失都会造成无法表达部分成功；应以人员明细为发放原子单位。
- 已发放后若允许原地修改，会破坏财务审计；首版应终态锁定。

## 当前结论

现有技术栈和用户、收款资料、发放、审计基础足以承载工资 MVP，不需要引入新框架或外部依赖；但工资人员范围、栏目公式、发放含义和普通用户可见性必须在实施前确认。
