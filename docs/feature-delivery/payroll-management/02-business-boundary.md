# 工资发放管理：业务边界

## 推荐业务模型

```text
工资期间（月） 1 ── * 员工工资明细 1 ── 0..1 工资发放凭证
                            │
                            └── 关联一个正式用户，并保存当月人员快照
```

## 核心对象

### 工资期间

- 用工资月份唯一标识，例如 `2026-09`，数据库统一保存为该月第一天。
- 保存期间状态、创建人、创建时间、锁定时间、完结时间和并发令牌。
- 状态建议为 `Draft`、`ReadyForPayout`、`Completed`、`Cancelled`。
- “部分已发放”由明细状态实时派生，不额外形成可手工修改的期间状态。

### 员工工资明细

- 一名用户在一个工资月份最多一条明细。
- 保存用户关联、姓名快照、工资组成、计算结果、备注、发放状态和并发令牌。
- 暂定工资栏目：基本工资、绩效工资、奖金、津贴、其他增加、社保个人扣款、公积金个人扣款、个人所得税、其他扣款。
- `应发工资 = 基本工资 + 绩效工资 + 奖金 + 津贴 + 其他增加`。
- `实发工资 = 应发工资 - 社保个人扣款 - 公积金个人扣款 - 个人所得税 - 其他扣款`。
- 所有金额保留两位小数且不得为负，实发工资必须大于等于零；计算结果由服务端生成。

### 工资发放凭证

- 一条工资明细最多一条发放凭证。
- 保存工资月份、实发金额、收款人姓名、银行卡尾号、确认人、确认时间和备注快照。
- 不保存完整银行卡号，不调用银行转账，不把管理员点击确认当作银行真实到账证明。
- 凭证一旦生成不可修改或删除。

## 人员范围边界

- 创建月份时默认快照当前启用且拥有 `Applicant` 角色的用户。
- 在 `Draft` 阶段，管理员可以从全部正式用户目录中补加人员或移除未发放人员，以覆盖离职结算、漏加等情况。
- 期间进入 `ReadyForPayout` 后人员范围固定，不再随账号启停、改名或角色变化而改变。
- 首版不把 `AppUser.IsActive` 解释为在职状态，也不建设完整人事档案。

## 状态机与写入边界

```text
Draft ──锁定──> ReadyForPayout ──全部明细 Paid──> Completed
  │                    │
  └──可取消            └──未发生任何发放时可退回 Draft

员工明细：Draft/NotReady ──期间锁定──> Pending ──确认发放──> Paid（终态）
```

- `Draft`：可增删人员和修改金额。
- 锁定：服务端重新计算全部明细并校验收款资料；存在错误则整月不能进入待发放。
- `ReadyForPayout`：金额和人员锁定，管理员逐人确认发放。
- 没有任何明细已发放时，允许退回 `Draft` 修正；已有一人发放后不允许退回。
- 全部明细发放后自动转为 `Completed`。
- 已发放差错不原地撤销，使用后续月份“其他增加/其他扣款”调整并填写原因。

## 权限与可见性

- `Administrator`：查看全部月份和人员、创建工资期间、填表、锁定、退回、确认发放、导出和查看审计。
- `Applicant`：暂定只能查看本人的 `Paid` 工资明细和发放时间；不能查看草稿、待发放金额、全员汇总或他人工资。
- 不新增第三种角色，不改变全局认证模型。
- 工资 API 独立授权，不能通过报销看板或用户目录间接返回工资金额。

## 与现有模块的边界

- 工资与报销、餐补分别核算、分别发放，不合并金额，不互相改变状态。
- 工资期间完成不触发报销归档，报销归档也不归档工资。
- 工资可复用个人姓名和银行卡资料，但历史工资只读取自己的快照。
- 工资不关联项目、周报、会议记录或报销凭证附件。

## 导出边界

- 管理员可按月份导出工资表 Excel，内容与该月固化明细一致。
- 如需银行代发文件，应另行确认具体银行模板、字段和安全传递方式；不将普通工资表直接声称为银行代发文件。
- 普通用户工资条导出列为建议项，待确认是否纳入首版。

## 明确不做

- 不建设考勤、请假、绩效、人事合同、部门岗位或自动计税系统。
- 不自动从周报、报销或餐补推导工资。
- 不接入真实银行、第三方薪资平台或税务申报系统。
- 不支持已发放工资的删除、撤销或原地修改。
- 不改变现有报销、餐补及其发放记录。
